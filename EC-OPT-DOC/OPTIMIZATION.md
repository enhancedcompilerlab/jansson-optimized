# 优化记录：字符串 token 扫描的批量 plain-run

> 全仓库仅改动一个文件：`src/load.c`。本优化已用差分测试证明与未改动基线**行为完全等价**（326 输入 0 不一致）。

## 一、改动的文件

| 文件 | 改动 |
|---|---|
| `src/load.c` | 唯一改动文件：为字符串 token 扫描新增"批量 plain-run"快速路径 |

## 二、优化了什么

**目标函数**：`lex_scan_string`（字符串 token 的逐字符扫描）。这是 jansson 解析的主热路径（profiling 显示逐字符读取 + 记账 + 逐字节 append 约占解析时间 60%）。

**原实现**：每个输入字节都过 `stream_get`（状态检查、UTF-8 校验、position/column 记账）+ `strbuffer_append_byte` 逐字节 append。

**优化**：当输入源是连续内存串（`json_loads`）且流内部缓冲为空时，把一段纯 ASCII 普通字符（`[0x20,0x80)` 且非 `"`/`\`）直接从源**批量 `memcpy` 进 `saved_text`**，`position`/`column` 按 run 长度一步推进，跳过逐字节的记账与分派。run 不含控制符、引号、反斜杠、高位字节，因此 UTF-8 校验、转义处理、错误定位全部仍走原路径——**构造性等价**。

## 三、为什么这是"编译器式优化"，而非算法改动

- 不改变算法：复杂度、扫描顺序、字节序、可观测状态全部不变。
- 只是把"对已知安全 run 逐字节重复的分派/记账"整体摊销（减少冗余 function call），等价于编译器把标量循环向量化/合并，而非替换更高效的算法。
- 保守编译器（GCC/Clang）不做这件事，是因为：① 函数指针抽象阻断跨函数推断；② `position`/`column` 被错误定位（`error->position`）读取、不可证明可合并；③ "哪些字节安全"是解析器语义，保守编译器不掌握。AI 恰好同时拥有这三类上下文。

## 四、正确性验证

差分测试（详见 `../ec-validate/`）：326 输入，**0 不一致**。

## 五、性能

进程内重复解析测吞吐（详见 `../ec-benchmark/`）。2 核云 VM 上绝对 MB/s 随负载浮动，相对增益稳定：

| 负载 | baseline | candidate | 提升 |
|---|---|---|---|
| 混合真实负载（0.91MB） | ≈37 MB/s | ≈39 MB/s | **+5%** |
| 字符串密集负载（0.86MB） | ≈112 MB/s | ≈213 MB/s | **+90%（近翻倍）** |

收益随字符串占比放大，印证优化命中字符串扫描的逐字节路径。
